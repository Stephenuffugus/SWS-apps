# SWS Studio — the design system

Sky Wolf Studios ships 23 free, ad-free, on-device apps. Before this system
they all looked like the same app wearing 6 accent colours: identical
`#f6f7f9` page, identical `#ffffff` card, identical `#1c2733` text, and one
`--accent` that repeated across four apps at a time.

The goal here is two things at once, and they pull against each other:

- **Each app should feel like its own product.** A caregiver log and a
  spinning-wheel picker have no business sharing a mood.
- **All 23 should obviously come from one studio.** Not a coincidence of
  hosting — a recognisable hand.

The resolution is that **geometry is shared and skin is not**. Spacing, type
scale, component shapes, focus behaviour, motion timing, the header, the
footer, the tip jar and the print rules are byte-identical in every app. Hue,
chroma, paper warmth, display face and background texture are not.

---

## How it is built

```
design/
  studio.css      the shared skeleton. Zero colour literals — consumes tokens only.
  skins.mjs       23 rows. One row per app: hue, chroma, paper, voice, texture, radius.
  color.mjs       OKLCH → sRGB, WCAG contrast, and the solver that guarantees both.
  build.mjs       skins + studio.css → design/out/<app>.css, with a contrast audit.
  apply.mjs       splices design/out/<app>.css into apps/<app>/index.html.
  preview.mjs     renders every skin side by side, and screenshots them.
```

To change anything:

```bash
node design/build.mjs      # regenerate tokens, run the contrast audit
node design/apply.mjs      # splice the base layer into all 23 apps
node design/preview.mjs --shots   # look at the result before believing it
```

`build.mjs --strict` exits non-zero if any contrast check fails. Wire that into
CI and a palette can never ship unreadable.

### Why the CSS is inline in each app rather than one shared file

Every app is an offline-first PWA. Its service worker is registered at
`/<app>/` and therefore only intercepts requests **inside its own scope**. A
shared `/studio.css` would sit outside all 23 scopes, so it would never be
served from cache, and every app would lose its styling the moment the user
went offline. That trades the core product promise for a cosmetic saving.

Inline also means one request instead of two and no flash of unstyled content.
The cost is 23 copies of the base layer, which is precisely what `apply.mjs`
exists to manage. The copies are delimited:

```css
/* ▼▼▼ SWS STUDIO BASE — generated by design/build.mjs. Do not edit. ▼▼▼ */
   ...tokens, then studio.css...
/* ▲▲▲ END SWS STUDIO BASE ▲▲▲ */

/* ═══ APP LAYER — rules specific to this app live below ═══ */
```

Re-running `apply.mjs` replaces everything between the sentinels and never
touches the app layer.

## Colour is computed, not picked

Every colour is specified in **OKLCH** and compiled to hex. Two reasons that
matters more than it sounds.

**Perceptual uniformity.** OKLCH lightness looks equally dark at every hue.
Choosing 23 palettes by hand in hex guarantees the yellow app comes out washed
and the blue app comes out heavy — they are the same "50% lightness" in HSL and
nowhere near it to a human eye. Here, `L = 0.605` is the same apparent weight
whether it lands on marigold or indigo, so the portfolio holds together.

**Contrast becomes an assertion.** Every derived token is solved against a real
WCAG target rather than eyeballed:

| token | must clear | against |
|---|---|---|
| `--ink` | 11:1 | canvas, surface, surface-2 |
| `--ink-2` | 4.6:1 | all three |
| `--ink-3` | 3.1:1 | all three |
| `--accent-deep` | 4.6:1 | all three (it is link text *and* a button fill) |
| `--accent-ink` | 4.6:1 | `--accent-deep` |
| `--focus` | 3.1:1 | all three (WCAG 2.2 SC 1.4.11) |
| `--line-2` | 3.05:1 | all three (control boundary, SC 1.4.11) |
| `--neg` / `--pos` / `--warn` | 4.6:1 | all three |

A token that misses gets walked along the L axis until it passes. The current
build is **1472/1472**.

Two consequences worth knowing:

- **`--ink` is hue-tinted**, not `#1c2733` for everyone. A warm app's near-black
  carries a trace of its own hue. It is why the same layout feels different
  between apps even before you notice the accent.
- **`--line-2` is genuinely 3:1.** The old `#e3e8ee` input border was about
  1.3:1 — invisible. Solving it properly is the single biggest reason the forms
  stopped looking unfinished, and it is a real accessibility fix, not taste.

## Token reference

Everything in `studio.css` is written against these. **The app layer must use
them too — never a hex literal.**

### Surfaces
| token | what it is |
|---|---|
| `--canvas` | the page. Tinted, never neutral grey. |
| `--canvas-2` | a recessed region of the page |
| `--surface` | a card |
| `--surface-2` | an inset well inside a card; also table headers, segmented-control track |
| `--field` | input background |
| `--line` | decorative hairline — card edges, row rules. May be faint. |
| `--line-2` | the boundary of an interactive control. Never use for decoration. |

### Ink
| token | what it is |
|---|---|
| `--ink` | body text and headings |
| `--ink-2` | secondary text, labels, hints. Still fully legible. |
| `--ink-3` | placeholders and disabled text only. Never a sentence the user must read. |

### Accent
| token | what it is |
|---|---|
| `--accent` | the mid-tone. Decorative fills, icons, non-text marks. |
| `--accent-deep` | link text, and the fill behind a primary button. Contrast-guaranteed. |
| `--accent-press` | hover/active state of a primary button |
| `--accent-soft` | tinted background fill — selected rows, highlight blocks |
| `--accent-ink` | the label that sits on `--accent-deep` |

### State & feedback
`--focus`, `--focus-halo`, `--neg`, `--neg-soft`, `--neg-line`, `--pos`,
`--pos-soft`, `--pos-line`, `--warn`, `--warn-soft`, `--warn-line`,
`--toast-bg`, `--toast-ink`, `--veil`.

The three semantic hues are rotated slightly toward the app's own hue, so a
warning in the terracotta app is a different warning from the one in the indigo
app. They read as part of the palette rather than three bootstrap colours.

### Type sizes — which token goes where

The audits kept flagging the same defect on app after app: the text that
*teaches* the user was the smallest text on the page. Hints at 12.8px sitting
under 16px body copy. So the rule is about role, not just size:

| token | px | use for |
|---|---|---|
| `--t-base` | 16 | body copy, list rows, empty-state guidance — anything read |
| `--t-sm` | 15 | hints, sub-lines, the colophon, the trust badge |
| `--t-xs` | 13 | **chrome only** — chip labels, the tip pill, a tagline |
| `--t-micro` | 12 | uppercase section labels and table headers, never a sentence |

If it instructs, explains, or reassures, it is at least `--t-sm`. `ul.plain > li`
is `--t-base` because in the list apps that *is* the content, not a footnote.

### Structure
`--s1`…`--s9` (4→56px), `--t-micro`…`--t-3xl`, `--lh-tight/snug/body`,
`--r` and its derivatives `--r-card` / `--r-ctl` / `--r-sm` / `--r-pill`,
`--shadow-0/1/2`, `--ease`, `--dur-1/2/3`, `--tap`, `--wrap`, `--measure`.

**Use the spacing scale.** A `padding: 13px` anywhere in an app layer is a bug.

### Legacy aliases
`--bg`, `--card`, `--muted`, `--chip`, `--chip-ink`, `--line-strong`,
`--paper`, `--paper-2`, `--ink-soft`, `--radius`, `--shadow` all resolve to
their modern equivalents via `var()`, so they follow dark mode correctly.

They exist so an app renders the instant the base lands. **New code should not
use them**, and migrating an app layer off them is part of finishing that app.

## The five identity axes

Hue alone cannot separate 23 products — the wheel only has 360°, so the average
gap is 15°, which is not enough to tell two apps apart. Four other axes carry
most of the work.

**1. Hue** — where the app sits on the wheel. Apps in the same hub category are
always pushed far apart, because those are the ones a user sees side by side.

**2. Chroma** — how saturated. Caregiver Log runs at `0.035` and Wheel Picker at
`0.175`. Two apps 15° apart at opposite ends of that range do not read as
related, which is the point.

**3. Paper** — `warm` gives the page a cream cast regardless of accent hue, so
the app feels like stationery. `cool` tints the page with its own hue and feels
like glass. After hue, this is the biggest "these are different products" lever,
and it is why Sitter Sheet and Bracket Maker feel unrelated despite both being
warm-ish.

**4. Voice** — which face heads the page. There are exactly three, because a
studio with 23 typefaces is not a studio:

- `editorial` — Fraunces. Warm, considered, paper-adjacent. Planning and
  ceremony: Specials Planner, Sub Plans, Sitter Sheet, Caregiver Log, Secret
  Santa, Wedding Timeline, Seating Chart, Signature Maker.
- `technical` — Space Grotesk. Precise, drawn, tool-like. Files and diagrams:
  PDF Tools, Scan to PDF, QR Maker, Bracket Maker, Moving Boxes, Home
  Inventory, Bill Splitter, Image Compressor, Signup Sheets, Team Parent,
  Wheel Picker.
- `plain` — the system stack, heavier and tighter. For apps where a neutral
  face is genuinely the right answer, not a cop-out: Baby Log, Pill Schedule,
  Grocery List, Packing List. These are read one-handed, in a hurry, sometimes
  by someone whose eyes are not what they were.

Body text is the **system stack in all 23**. It renders instantly, costs zero
bytes, and is the through-line under everything else.

**5. Texture** — one background signature from a fixed vocabulary: `wash` (two
soft colour fields at the corners), `grid` (faint graph paper, for tools that
produce a diagram or a record), `grain` (paper tooth, at 3.5% — above 4% it
stops reading as paper and starts reading as a broken screen), `band` (a solid
accent bar at the top), `rule` (a single accent hairline), `none`.

## The component contract

`studio.css` styles these. An app layer may extend them; it should not restate
them.

**Chrome** — `header.app` (+ `img`/`.mark`, `h1`, `.tagline`, `.spacer`),
`a.tipbtn`, `.hero`, `footer.colophon`, `.trust`, `#toast`, `.skip`.

**Layout** — `.wrap`, `.stack` (+ `.stack-sm` / `.stack-lg`), `.cluster`,
`.row`, `.frow`, `.tablewrap`, `.actionbar`.

**Surfaces** — `section.card` / `.card` (+ `> h2` micro-label, `.sub`), `.well`.

**Controls** — all text inputs, `select`, `textarea`, `input[type=checkbox]`,
`input[type=radio]`, `label.f` (+ `> span`), `.field`.

**Buttons** — `.btn` and `.primary` / `.danger` / `.ghost` / `.plain` /
`.small` / `.big` / `.block` / `.icon`.

**Segmented** — `.seg` (+ `button` / `.tab`, `.active`).

> `.seg` carries no ARIA of its own, deliberately. Three apps shipped
> `role="tablist"` on it with plain `<button>` children, which axe flags as a
> **critical** violation (`aria-required-children`) — a tablist whose children
> are not tabs is worse than no role at all, because it lies to a screen reader.
>
> Pick one and do it fully:
> - **Toggle-button group** (almost always the right answer here): no role on
>   the container, and `aria-pressed="true|false"` on each button. Nothing else
>   is required and it needs no keyboard handling beyond Tab.
> - **Real tabs**: `role="tablist"`, `role="tab"` + `aria-selected` +
>   `aria-controls` on each button, `role="tabpanel"` + `aria-labelledby` on the
>   panels, roving tabindex, and Left/Right arrow-key navigation. Only take this
>   on if you are going to implement the keyboard behaviour.

**Small type** — `.hint`, `.footnote`, `.small`, `.em`, `.muted`, `.chip`
(+ `.on`), `.chips`, `.warn`.

**Empty state** — `.empty` (+ `.glyph`, `h3`, `p`).

**Utility** — `.hidden`, `.sr-only`, `.nowrap`, `.tnum`, `.noprint` /
`.no-print` / `.screenonly`, `.printonly`.

### What belongs in the app layer

Only what is genuinely unique to that app: the bracket tree, the wheel canvas,
the week grid, the seating floor plan, the QR preview panel. Anything that is
"a card with a heading and some fields" is already handled.

### Rules for the app layer

1. Tokens only — no hex, no `rgb()`, no magic px outside the spacing scale.
2. Do not restyle `.btn`, `.card`, inputs, or focus. If a component is wrong for
   your app, it is probably wrong for others; fix `studio.css`.
3. Body text never below `16px`. Inputs never below `16px` — anything smaller
   makes iOS Safari zoom on focus, which reads as broken.
4. Interactive targets are at least `var(--tap)` (44px).
5. Never remove a focus style. Never set `outline: none` without an equally
   visible replacement.
6. If the app produces a printed artifact, its print rules go here and are
   tested by actually printing to PDF.

## Non-negotiables

**Accessibility.** Contrast is enforced by the build. Beyond that: every control
has an accessible name, icon-only buttons carry `aria-label`, async status goes
through a live region, heading order is not skipped, and every custom widget is
operable from the keyboard. `prefers-reduced-motion` and `prefers-contrast: more`
are honoured in the base and must not be undone.

**Print.** Half the portfolio exists to produce a piece of paper — a fridge card,
a sub binder, a seating plan, a sitter sheet. The base ships a real print
stylesheet: white ground, black ink, chrome hidden, cards unbroken across pages,
`@page` margins. Printing is a feature, not an afterthought.

**Offline.** Nothing may introduce a network dependency. No CDN, no Google
Fonts, no remote image. If a font is used it is self-hosted inside that app's
own directory so its service worker can cache it — and added to the SW asset
list, or it silently breaks offline.

**The promise.** *Nothing leaves your device. No account. No ads. No
subscription.* The `.trust` component exists because research says users do not
believe that claim as grey body copy at the bottom of a page. It has to look
like a stamp on the thing.

**The thumb zone is sacred.** This one comes straight out of the research and it
is the sharpest thing the portfolio can differentiate on.

Across 12 apps' worth of competitor reviews, the complaints that carry real
anger are not about price — they are about a UI engineered to make you tap the
wrong thing. Cozi's upsell banner *"starts small and increases in size just as
users are about to click on a list."* Baby-tracking apps render promotional
popups **inside the log list**, so a half-asleep parent at 3am taps an upgrade
prompt instead of the feed button. Glow shows a breast-pump ad every time you
log a pump.

So, as a hard invariant, not a preference:

- **Nothing appears over a primary surface.** No interstitial, no banner, no
  modal that the user did not open. The log screen renders the same pixels
  every single time it opens.
- **Nothing in the thumb zone moves, grows, or animates.** Layout in the lower
  half of a phone screen is static. Transitions there may change colour; they
  may not change size or position.
- **The tip jar is an offer, never a nag.** It sits in the header — top of the
  screen, out of the thumb path — as a quiet outlined pill. It never animates,
  never overlays, never appears mid-task, and never sits between the user and
  the thing they came to do. On apps with a clear completion moment (a Secret
  Santa draw, a finished PDF), the right place for a second mention is *after*
  the job is done.
- **No affiliate links, no store, no sponsored placement, ever.** There is
  nothing to go stale and nothing that can pay to appear in a user's list.

These are worth stating as absolutes because they are the product. Every
incumbent in every one of these categories has a commercial reason it cannot
follow them, and we do not.
